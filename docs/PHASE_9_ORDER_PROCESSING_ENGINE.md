## Universal Order Model

`OrderRun` now acts as the universal order envelope and includes:

- `header`
- `poNumber`
- `orderNumber`
- `sourceType`
- `sourceFileName`
- `sourceMetadata`
- `processorProfileId`
- `processorType`
- `processorVersion`
- `lines`
- `outputArtifacts`
- `errors`
- `parseWarnings`

`OrderLine` now carries:

- source row position
- provided item number, UPC, description, quantity, unit, and unit price
- matched internal item number
- validation status, method, confidence, candidates, and errors
- raw source row

This gives the console and audit trail enough data to show what was extracted, how it was validated, and what still needs human review.

## Processor Registry

The backend now supports these `processorType` values:

- `csv`
- `xlsx`
- `xls`
- `xlt`
- `pdf`
- `emailBody`
- `customerOverride`

Processor selection order is:

- explicit `processorProfileId`
- explicit `processorType`
- customer-scoped `processorProfiles`
- tenant-global `processorProfiles`
- default `csv`

Customer-specific behavior should be represented as `processorProfiles` data, not new flow branches. `customerOverride` delegates to a concrete base processor with profile settings such as `fieldMap`, `linePattern`, `baseProcessorType`, `hasHeader`, `headerlessColumns`, or `delimiter`.

## CSV Parse Migration

`orderProcess - CSV Parse` is the only active CSV flow in scope. The two deprecated CSV variants remain out of scope.

The replacement path is implemented in `CsvOrderProcessor`:

- Uses Python's standard `csv` parser.
- Supports headered and headerless CSV.
- Supports delimiter sniffing with fallback to comma.
- Supports configurable headerless columns.
- Supports field maps for customer-specific source headers.
- Handles UTF-8 BOM and Windows code-page BOM artifacts.
- Produces canonical `OrderLine` records directly.

No Plumsail CSV parsing or conversion connector is used by the new backend path.

## Workbook Processing

`XlsxOrderProcessor` reads simple XLSX workbooks with standard-library ZIP/XML parsing. It supports inline strings and shared strings and maps the first worksheet into canonical rows.

`LegacyWorkbookOrderProcessor` supports:

- caller-supplied `sourceRows`
- HTML-backed XLS/XLT exports like the Phase 2 fixtures

Binary BIFF XLS/XLT files are explicitly marked with `legacyWorkbookConversionRequired` until a backend conversion module is added or pilot data proves a narrower path is enough. This keeps the replacement path in Azure code and avoids introducing a new Plumsail-style connector.

## PDF Processing

PDF extraction is represented through Azure Document Intelligence, not Google Document AI.

`PdfOrderProcessor` accepts:

- `documentIntelligenceResult`
- `extractedText`
- `sourceRows`

Raw PDF bytes without extracted tables/text produce `documentIntelligenceExtractionRequired` and create a parser-failure exception task. The deployed extraction boundary is represented by `AzureDocumentIntelligenceExtractor`, which uses `DocumentIntelligenceClient.begin_analyze_document` with a default `prebuilt-layout` model.

## Email Body and Customer Overrides

`EmailBodyOrderProcessor` supports:

- pipe-delimited body tables
- simple line patterns like `item-upc-quantity`
- PO extraction from subject/body text

`CustomerOverrideOrderProcessor` delegates to a configured base processor. The Market Place Pet Supplies style fixture is covered by a profile-driven email-body regex:

```json
{
  "baseProcessorType": "emailBody",
  "linePattern": "(?P<provided_upc>\\d{12})-(?P<quantity>\\d+)"
}
```

## Output Generation

Every processed order still receives:

- `universalOrderJson`
- `lineCsv`

When an output profile or request asks for XLSX, the backend adds `lineXlsx` as base64 content generated by `order_to_xlsx_bytes`. This is intentionally code-generated in the Azure Function layer and does not use Plumsail.

## API and Cosmos Updates

`POST /orders/{orderRunId}/process` now accepts:

- `processorProfileId`
- `processorType`
- `processorSettings`
- `fieldMap`
- `sourceContent`
- `sourceContentBase64`
- `sourceRows` or `rows`
- `bodyText`
- `extractedText`
- `documentIntelligenceResult`
- canonical `lines`

Parser failures create `exceptionTasks` with `taskType: parserFailure`. Unresolved or possible item matches continue to create `itemValidation` tasks.

`order.processed` audit events now include processor type, source type, status, and line count.
